# 5教材の観測・契約・学習課題

Javaが実行し、Pythonが記録を再生して契約を評価する。これはJavaからPythonへの一般的なプログラム翻訳ではない。
以下の分析は、異言語の境界で残す情報と、その情報を使って説明できる学習課題を対応付ける。
圏論の用語そのものを初学者の習得目標にはしない。授業への効果は未評価である。

実装済み機能と授業提案の区別、90分授業案、採点規準は [TEACHING_GUIDE.md](TEACHING_GUIDE.md)、
境界検証と独立言語間比較の対象版・実行手順は [REPRODUCIBILITY.md](REPRODUCIBILITY.md) にまとめている。

| 教材 | 残す情報 | 問い・契約 | 捨てると区別できないこと |
|---|---|---|---|
| 参照と同一性 | 参照先ID、更新先、値 | 2本の参照が同じBoxへ到達するか | 値が同じ別のBoxと共有されたBox |
| Strategy | 保持参照、呼び出し先の履歴、料金 | 選択した実体へ委譲したか | 入力0で同じ値を返す異なる委譲 |
| State | 状態タグ、回数、操作境界 | 現在状態に応じた遷移か | 同じ回数でも次の要求への応答が違う状態 |
| Observer | 区間開始時の登録列、区間内の通知先列 | 登録回数どおりに通知したか | 重複登録・通知欠落。順序は現在の契約で忘れる |
| Abstract Factory | 要求系列、製品参照、呼び出し対応、文字列と復号値 | 製品群が揃い、合成が値を保存するか | 偶然の往復一致と系列違反、誤った合成 |

## 1. 参照と同一性

Java側の`References.a`と`b`はフィールドであり、同じBoxを参照すると更新先を共有する。
Pythonの辞書の内容比較だけで代替せず、同一性をIDと参照辺で表す。
値だけへ写す観測では、入力0の正常例と比較例で共有を区別できない。
これは「異なる実行を同じ観測に潰すなら、その違いを問う契約は判定できない」という観測の因子化条件の具体例である。

授業ではalias地点で参照図を予測し、b経由の更新後にaから見える値を説明させる。
採点は数値だけでなく「二つの値が同期するのではなく同じ格納場所に到達する」と説明できるかを含める。
転移課題は同じ初期値を持つ別インスタンスへの変更とする。配列、文字列intern、equalsの一般論はこの教材では検証しない。

## 2. Strategy

型の適合、値の仕様、選択済みの実体への委譲を区別する。
入力0では正常例・比較例の全チェックポイントと最終結果が一致するため、状態だけの表示では委譲ミスを判断できない。
Python側は呼び出し先の履歴を保ち、regular→discountという順序を検査する。
料金方式を交換することは、同じ料金関数を保存する自然変換とは限らない。100→100と100→80は実際に異なる。

学習者はswitch地点で宣言型と実際の参照先を記し、2回目の呼び出し先を予測する。
入力100と0の比較から、出力が同じでも同じ設計判断とは限らないことを説明する。
新方針を追加する転移課題では、Clientが具体クラスの分岐を増やさず委譲できるかを検討する。
固定した2回の呼び出し先を検査する実装であり、任意の選択列に関する一般的な委譲不変条件は未実装である。

## 3. State

意味のある状態は(状態タグ, 通過回数)である。回数だけが同じでもLockedとOpenは同じ要求へ異なる応答を返す。
状態タグを忘れる写像は、後続の操作によって再び区別される状態を併合するため、次状態を計算できる商モデルを与えない。
他方、更新済みの値を受信する再生器はそれを表示できる。「予測する意味モデル」と「ログを読む再生器」を区別する根拠になる。

ready・unlock・passで状態タグと回数を別々に予測し、比較例が最初に仕様から外れる境界を示す。
Strategyとの比較では図の類似より、方針を選ぶ責任と状態遷移を担う責任の違いを説明させる。
現在のAPIはrequest(next)であり、call.argは固定値0でnextを記録しない。任意の要求列を評価するならイベント形式の追加が必要である。

## 4. Observer

通知先の列を出現回数へ写すCounterは連結を加算へ写し、空列を0へ写す。
これは順序を忘れる合成保存の具体例である。順序を保存しなくても、この教材が定める回数の契約には十分である。
集合にすると重複の回数まで失うため、同じ簡略化とは言えない。

学習者はsubscribe後の登録先とremove後の登録先を予測し、各cycle内の通知履歴と対応付ける。
教師用の発展課題では順序を反転した実装を提示し、それを直ちに誤りと呼ばず、契約が順序を要求するか説明させる。
共有状態、再入、通知中の登録変更を導入するなら、順序を忘れてよいか再検討する必要がある。
現在の判定は通知引数やreturnとの対応を完全には検査しない。追加教材のschema 2の保証をObserverへ読み替えてはならない。

## 5. Abstract Factory

ClientはFactoryからEncoderとDecoderを取得し、十進・十六進を同じ処理で実行する。
Python側へ必要なのはクラス名だけでなく、戻り参照と保持参照、encodeの戻り文字列とdecodeの入力、復号値と例外の区別である。
生成元の対応は手動記録に基づく。newは登録を示し、JVM上での割当てや新鮮性の証明ではない。

仕様の圏を対象Value・Codeと射e: Value→Code、d: Code→Value、関係de=idで提示すれば、正常な系列はその関係を保つモデルになる。
同じ形のインターフェースを持つだけの混在系列は、この関係を保つモデルとは限らない。
Factoryオブジェクト自体をそのまま関手と呼ぶのではなく、製品の操作が仕様の対象・射・関係をどう実現するかを定める。
往復変換則はこのcodecの契約であり、Abstract Factory全般の公理ではない。

授業は入力0・16・10の予測から始める。比較例はそれぞれ偶然の一致、値の不一致、解析例外になる。
系列整合と往復変換を別々に説明させ、修正後は未見の入力で確かめる。
「両製品を十進へ揃える」修正は往復変換を回復しても、十六進を要求した契約を満たすとは限らない。
この追加の誤実装はGUIの第3variantとしては収録せず、授業でコードを変更する発展課題とする。

## 教材作成・評価への反映

学習目標→判定する契約→必要な観測→正常・違反・契約を保つ別実現→根拠付き説明、の順で設計する。
追加教材では、この手順から文字列・製品参照・例外終端を含むschema 2を導いた。
状態再生・図・後退操作は再利用し、固有契約をfactory_contract.pyへ分けた。
入力上限はPython側で共有したがJavaでも独立に制限し、両側の一致を検証する。

判定欄は全記録の結果を示すため、予測の記入を先に行う。提出・採点・答えを隠す機能は未実装である。
教育評価では、未見の例の予測、根拠イベントの選択、契約に沿う説明、修正後の転移を区別して採点する。
この順序が実際に学習効果や作成時間を改善したという実験結果はまだない。
